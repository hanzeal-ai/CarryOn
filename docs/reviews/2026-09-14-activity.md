# 动态 / activity 独立审查（2026-09-14）

结论：有条件接受当前本机 workspace、cloud transport 与 iOS 展示切片。重新审查完整 transport 后，原先“binding 级 reader 足以证明隔离”的结论已修正：同一 binding 下多账号的清已读隔离现在依赖已认证 console session identity 派生出的账号级 `activity_cleared` owner，而不是请求体提供的字段。远程 clear-read 缺少已验证账号身份时现在返回 409，避免新本机遇到旧网关时静默退回 binding 级共享清理。审查范围内没有发现必须修改的问题。

边界：本次审查当前修改中的 `carryon/workspace.py`、`carryon/timeline.py`、`carryon/api.py`、`carryon/remote_scope.py`、`carryon/gateway.py`、`carryon/console.py`、`carryon/cloud.py`、`iOS/CarryOn/App/ProjectsView.swift`、`iOS/CarryOn/App/Design.swift`、`iOS/CarryOn/App/ConversationView.swift`、`tests/test_workspace.py`、`tests/test_onboarding.py`。没有验收 app-server、生产环境、真实 APNs、真实 iPhone 点击/视觉效果，也没有批准部署、迁移、提交或推送。

## 审查要点

- `activity_cleared` 以 `(reader, thread_id)` 为主键保存清理游标。`clear_read(reader, activity_owner)` 只把 clear cursor 写入 `activity_owner or reader`，但判断“是否已读”的 join 仍使用基础 reader 和 `native:codex`；因此新增账号级 owner 只影响 retained activity 的清理/查询，不擅自改变既有 binding 读游标、通知偏好或 native read 语义。见 `carryon/workspace.py:30`、`carryon/workspace.py:117-138`、`carryon/workspace.py:143-155`。
- 投影仍用 reader 自己的 `notification_readers` 加全局 `native:codex` 计算 unread，并用 `activity_owner or reader` 查询 `activity_cleared`；这保留旧 unread/pending/badge 合约，同时让同一 binding 下不同账号的“清已读”互不串扰。见 `carryon/workspace.py:169-184`、`carryon/workspace.py:193-200`。
- 默认 `/api/activity` 仍只返回 `activity`，`includeRead=true` 才纳入 `activityRetained`；已读历史不会进入旧 badge 合约。见 `carryon/workspace.py:232-249`、`carryon/workspace.py:253-257`。
- console 侧在设备请求代理前把 `activity_owner` 设置为当前认证 session 的 identity；随后 delegated gateway request 只从 handler 属性取顶层 `activityOwner` 传给 device.call，未使用浏览器请求体或顶层伪造字段。见 `carryon/console.py:442-459`、`carryon/gateway.py:129-134`。
- cloud connector 将 gateway 下发的 `activityOwner` 作为独立参数传给 scoped dispatch；`remote_scope` 对远程 `POST /api/notifications/clear-read` 强制要求该身份，缺失时返回 409；身份存在时只接受 `[A-Za-z0-9_-]{1,100}`，并派生为 `binding:<binding>:account:<identity>`，原始 body 内字段不会参与派生。见 `carryon/cloud.py:90-100`、`carryon/remote_scope.py:25-40`。
- remote read-only binding 可继续调用 workspace 的 clear-read/read/preferences 路由；clear-read 的账号级 owner 只用于 retained 清理，不扩大到通用写入权限。见 `carryon/remote_scope.py:33-39`。
- 完成时间来自原生 turn 的 `turnStartedAtMs + durationMs`，仅 completed 且数值有限非负时输出；不会退化为 catalog 更新时间或当前时间。见 `carryon/timeline.py:115-129`。
- iOS 动态页使用 `/api/activity&includeRead=true` 保留已读动态，清已读调用 `POST /api/notifications/clear-read` 后重新加载并刷新计数；已读行只是传给 `ThreadRow(dimmed:)`，仍在 `Button { select(record) }` 中，跳转行为保留。见 `iOS/CarryOn/App/ProjectsView.swift:103-108`、`iOS/CarryOn/App/ProjectsView.swift:143`、`iOS/CarryOn/App/ProjectsView.swift:163`。
- `ThreadRow` 优先展示 `projectName`，完成会话显示 `completedAt`，已读 retained 行通过去饱和与透明度变灰，不禁用交互。见 `iOS/CarryOn/App/Design.swift:90-119`。会话详情 turn header 也显示完成时间，见 `iOS/CarryOn/App/ConversationView.swift:294-300`。

覆盖到的关键契约：

- `test_read_activity_retained_cleared_per_reader_and_new_events_return` 验证已读动态 retained、默认 activity 不计已读、清理仅影响当前 reader、不删事件、不删 session、重启后清理保持、新未读事件在 clear race 后重新出现。见 `tests/test_workspace.py:179-201`。
- `test_native_read_clear_and_readonly_remote_clear` 验证 native read 后 remote binding 可清自己的 retained activity，且另一个 binding 不受影响。见 `tests/test_workspace.py:203-210`。
- `test_clear_read_pending_activity_does_not_answer_request` 验证清已读不会回答/取消审批请求，pending activity 仍按旧合约计数。见 `tests/test_workspace.py:212-218`。

- `test_completion_uses_native_time_not_catalog_update` 验证完成时间来自 native turn timing，并拒绝未完成或缺字段 turn。见 `tests/test_workspace.py:229-237`。
- `test_activity_owner_is_derived_from_login_not_request_body` 验证 console 设备请求下发给 device.call 的 `activityOwner` 来自登录 identity，而不是顶层或 body 伪造字段。见 `tests/test_onboarding.py:135-149`。
